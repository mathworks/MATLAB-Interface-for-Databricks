Building Wheel libraries with MATLAB

A Wheel library is a Python® package form for a library, and is a file with a .whl extension.

Introduction

This utility, the PythonSparkBuilder, uses MATLAB® Compiler SDK™ to create a Python library, and then generates wrapper code that will enable the use of the underlying compiled MATLAB® functions in a Spark context.

The methods applied to a Spark DataFrame (mapInPandas) or an RDD (map, mapPartitions), act on a chunk of a DataFrame. This could be seen as a table in MATLAB®. Other methods, User Defined Functions (UDFs), can be applied to one or more columns of a DataFrame.

Using this functionality has as prerequisites MATLAB® Compiler SDK™ (and dependent toolboxes), as well as a Python installation and any needed libraries. Please see MATLAB®/Python version compatibility It's important that the Python version and its libraries correspond to the libraries used in the Spark installation where it will be used.

Basic usage

The basic workflow will be described by some simple examples.

Setup

These examples, located in a directory, something like this: /<somewhere>/[Databricks|Spark]/Modules/matlab-spark-api/Software/MATLAB/examples/compiler

The exact location can be found by executing this in MATLAB®:

getSparkApiRoot('examples', 'compiler')

This directory contains several MATLAB® functions, that show different examples of how to write a function, that can be used in a Spark context.

Note: If using the Databricks® package, please also see examples in the directory databricksRoot('examples', 'DatabricksConnect')

Building the wheel

All functions are compiled into the same Wheel file, but this is completely arbitrary. The user decides what files to compile into which library, and separate libraries could be built for all functions in this example.

Before the functions can be compiled, schema files must be generated.

Generating the schemas

The schemas are generated by calling the function generateFunctionSchema with the name of the function, as well as any arguments for it.

In the first case, plusPi just takes a double argument:

function pp = plusPi(x)
    pp = x + pi;
end

Note: The way schemas are now generated, i.e. generating a myfun.schema from myfun.m, used to be generating a signature myfun_signature.json from myfun.m. This is still supported, but discouraged. The new schema relies on the schemas used by Apache® Spark™, and so is a better fit. It furthermore supports more Datatypes, notably StructType and MapType. The previous method is deprecated and will be removed in a future release.

Generate the schema like this:

generateFunctionSchema("plusPi", {33})

This will generate a Schema file like this:

{
  "type": "compiler",
  "funcname": "plusPi",
  "fullFilename": "/Somewhere/plusPi.m",
  "inputs": [
    {
      "type": "io",
      "Name": "x",
      "Direction": "in",
      "Table": false,
      "SparkType": "double"
    }
  ],
  "outputs": [
    {
      "type": "io",
      "Name": "pp",
      "Direction": "out",
      "Table": false,
      "SparkType": "double"
    }
  ]
}

It's not important that the number 33 was used, just a double value in this case. Note that the output types weren't specified in the call. They are determined by MATLAB® calling the function with the argument(s) specified.

This is done to provide the MATLAB® build with more information about the data it will act on. This takes away some of MATLAB®'s versatility with respect to data types, but for a good reason. When running on Spark, there is marshalling going on between Spark, Python and MATLAB®. The marshalling code can be more efficient if it's determined at compile time what the types are. Furthermore, the Spark Dataframes have specific types, so it's good to adhere to these types.

Note: More information on this is covered in Function Signatures.

The second function, doMath, takes 2 double arguments:

function [x,y] = doMath(a, b)

    y = int64(a*b);

The last function, addStringCol, takes a Dataframe as an argument (in Spark).

function T_OUT = addStringCol(T_IN)
    T_OUT = T_IN;
    T_OUT.hello = string(T_IN.id) + "_hello_" + string(T_IN.did);
end

All the previous code can be found in the function generateSchemas.m in the same directory.

Note: It should be noted that Spark doesn't guarantee that the chunks of a sorted table remains sorted. When a table is used in a context where ordering is of essence, this should be taken into account. As an example, if the table is providing input to a Simulink® model with a time vector and a corresponding value, these must be sorted. Simulink® will only accept a monotonically increasing time vector, and will fail otherwise. Depending on the model, it may also be necessary to shift the first time value to be zero.

Furthermore, the resulting Dataframe doesn't have a guarantee on sorting either, so if sorting is of essence, the user of that Dataframe must ensure this manually, for example using orderBy or sort.

A typical example for ordering the data used in the MATLAB® function may look like this:

    % Sort the time
    data = sortrows(data, 't');

    % Reset to zero starting time
    data.t = data.t - data.t(1);

Compiling the code

To compile the code, an option object is first created, and the code is then built with this:

% First create the opts object
opts = compiler.build.PythonPackageOptions(...
    ["plusPi.m", "doMath.m", "addStringCol.m"], ... % the files to compile
    "OutputDir", "_build", ...                 % the output directory
    "PackageName", "mypackagename");                     % the package name

% Then compile the code (note the `spark` in the function name)
PSB = compiler.build.spark.pythonPackage(opts);

At this point, there should be a wheel present in the corresponding dist folder:

$ dir _build/dist/
mypackagename-24.2.0-py3-none-any.whl

The code above is also present in buildLibrary.m in the same directory.

Providing the Wheel file to the cluster

If this wheel file is used in a Spark/Databricks environment, the following steps are required:

To run the file, it must be available on the cluster, and different clusters may have different options for this.

In the case of Databricks, several methods and options exist to handle the wheel files more easily.

The PythonSparkBuilder class has a method uploadWheelFile which will upload the wheel file to databricks. This method can be called on the result object of the build. The method takes the path to the wheel file as an optional named argument destination like this:

PSB.uploadWheelFile(destination="/Volumes/main/default/myvolume/mywheelfiles");

Alternatively, the compiler.build.spark.pythonPackage' function takes the optional named argument wheelDestination, which allows the user to specify the future destination of the wheel file. If this was used, the uploadWheelFile` can be called as follows:

PSB.uploadWheelFile();

It's also possible to directly install the wheel file on the cluster using the installWheelOnDatabricksCluster method. This used to be the only way to install a wheel file for use with Databricks, but is now used less, as it is less flexible compared to methods which install a wheel file in a Spark Session. Please refer to the notes on %pip install below.

The method still exists, though, and can be used as follows:

PSB.installWheelOnDatabricksCluster("/Volumes/mycatalog/myschema/myvolume/some/directory", clusterId=cluster_id);

Note: addArtifact is an alternative method of provisioning a library to a Databricks cluster, it is used with Databricks/Spark Connect. Note: If the cluster defines a library using a policy, thus further libraries cannot be installed using the Libraries API. To install the library use the %pip command in a notebook: %pip install /Volumes/mycatalog/myschema/myvolume/some/directory/my.example-24.2.0-py3-none-any.whl If a new version of a library is installed, it may need the additional option --force-reinstall See Notebook scoped libraries in the LibraryAPI in the Databricks documentation.

Importing to the environment

The functions to use with Spark will be created in a module called wrapper. In order to call a specific function, import it from the package.

This code is assumed to be running in a Notebook.

# First, import the Wrapper class of this package
from mypackagename.wrapper import *

To simply call a function (will activate the MATLAB® runtime):

# Test the function detectAnomaly
T = plusPi(10.0)
# T == 13.14...

doMath takes 2 arguments:

M = doMath(5.0, 7.0)
# M == (12,35), a tuple, as two return values

addStringCol expects a Dataframe with two columns, an int and a double:

# DF  is a Dataframe as described
OUT = DF.mapInPandas(addStringCol_applyInPandas, addStringCol_output_schema)
OUT.show(3)

For the previous function, it needs a pointer to the function (addStringCol_applyInPandas), as well as the schema of the output (addStringCol_output_schema). Both are generated, and part of the wrapper import.

Example functions

For each function that was compiled, there is an example file:

$ dir _build/examples
addStringCol_example.py
doMath_example.py
plusPi_example.py

Note: The examples are simple, and only use artificial data. They may, however, prove helpful to a MATLAB® user getting started with Spark, rather than as a guide to writing Spark jobs.

The example files have this general form:

  • Imports of available functions

  • Creation of trivial data with correct types

  • Examples of calling the functions in a Spark context

The import can look like this:

# Import special functions from wrapper
from mypackagename.wrapper import addStringCol_output_names
from mypackagename.wrapper import addStringCol_output_schema
from mypackagename.wrapper import addStringCol_mapPartitions
from mypackagename.wrapper import addStringCol_applyInPandas
from mypackagename.wrapper import addStringCol_mapInPandas

The example data looks something like this;

# Create some trivial input data with the right data types
DATA = [
    (    int(1),    float(1),    ), 
    (    int(2),    float(2),    ), 
 # ...
    (    int(98),    float(98),    ), 
    (    int(99),    float(99),    ), 
    (    int(100),    float(100),    )
]

Finally, examples may look like this:

print("### Run applyInPandas with addStringCol")
DF_applyInPandas = DF.groupBy("id").applyInPandas(addStringCol_applyInPandas, addStringCol_output_schema)
DF_applyInPandas.show(10, False)

Or like this:

# Create a database view of the data
DF.createOrReplaceTempView('temptest_doMath')

# Register as UDF
doMath_reg_udf(spark)

# Use the UDF on the temporary table
UDF1 = spark.sql('SELECT a, b, doMath_udf(a, b) FROM temptest_doMath')
UDF1.show(5, False)

Using UDFs

There are different flavours of UDFs that can be used. Not all function signatures can be used as UDFs however.

This will generate the following helper functions that registers the corresponding function as a UDF. The helper functions for registration (<fcn_name>_reg_udf*) are generated with the package. The shown usage can be done in a notebook.

Note: The usage examples shown here are taken straight from the generated example files, and can be used as a starting point.

Basic UDF, for use with SQL

def plusPi_reg_udf(spark, name='plusPi_udf'):
    """ Register the function plusPi as a UDF
    A second argument can be used to specify the name to be used."""
    spark.udf.register(name, plusPi, DoubleType())

def doMath_reg_udf(spark, name='doMath_udf'):
    """ Register the function doMath as a UDF
    A second argument can be used to specify the name to be used."""
    spark.udf.register(name, doMath, doMath_output_schema)

As can be seen in these definitions, the registered UDFs are given a default name (<fcn_name>_udf), but a different name can be chosen using a second argument.

These can then be used as follows for plusPi:

# Register as UDF
plusPi_reg_udf(spark)

# Use the UDF on the temporary table
UDF1 = spark.sql('SELECT X, plusPi_udf(X) FROM temptest_plusPi')
UDF1.show(5, False)

And as follows for doMath:

# Register as UDF
doMath_reg_udf(spark)

# Use the UDF on the temporary table
UDF1 = spark.sql('SELECT X, Y, doMath_udf(X, Y) FROM temptest_doMath')
UDF1.show(5, False)

Evidently, after registering one of the previous UDFs, they can be used in SQL cells too.

%sql
SELECT X, Y, doMath_udf(X, Y) FROM temptest_doMath

Basic UDF, for use with Dataframes

def plusPi_reg_udf_dataframe():
    """ Returns a UDF function for use with Dataframes."""
    return udf(plusPi, DoubleType())

def sqcombo_reg_udf_dataframe():
    """ Returns a UDF function for use with Dataframes."""
    return udf(sqcombo, sqcombo_output_schema)

Use this for plusPi:

# Register as UDF for Dataframes
plusPi_udf_df = plusPi_reg_udf_dataframe()

# Use in a Dataframe select statement
UDF2 = DF.select('X', plusPi_udf_df('X'))
UDF2.show(5, False)

And use this for doMath:

# Register as UDF for Dataframes
doMath_udf_df = doMath_reg_udf_dataframe()

# Use in a Dataframe select statement
UDF2 = DF.select('X', 'Y', doMath_udf_df('X', 'Y'))
UDF2.show(5, False)

Use a Panda Iterator-Series UDF

These functions are similar to the previous ones, but with the difference that the input data will be an iterator of Pandas Series objects. This might be useful when needing to use different batch sizes for memory reasons, cf. Setting Arrow® batch size.

def plusPi_reg_udf_series_iter():
    """ Register the function plusPi_series_iter as a pandas_udf function.
    It may be used as follows:
      plusPi_pandas_udf_iter = plusPi_reg_udf_series_iter()
      DF.select(plusPi_pandas_udf_iter(col('arg_x')))
    """
    return pandas_udf(plusPi_series_iter, DoubleType())

def doMath_reg_udf_series_iter():

    """

Use it for plusPi:

# Register as UDF for Pandas iterator-series
plusPi_udf_series_iter = plusPi_reg_udf_series_iter()

# Use in a Dataframe select statement
UDF4 = DF.select('x', plusPi_udf_series_iter(col('x')))
UDF4.show(5, False)

And for doMath:

# Register as UDF for Pandas iterator-series
doMath_udf_series_iter = doMath_reg_udf_series_iter()

# Use in a Dataframe select statement
UDF4 = DF.select('a', 'b', doMath_udf_series_iter(col('a'), col('b')))
UDF4.show(5, False)

Note: Each environment (Apache Spark, Python and MATLAB®) have a certain set of supported data types. Often, there's a direct mapping between some types, and for others there's no exact mapping. For example, Spark supports (amongst others) int16, int32 and int64, and so does MATLAB®. Python however, supports one integer type, of potentially unlimited bits. This can lead to cases where the implementation difference cause numeric differences in output. To see a complete list of data types supported with this workflow, please refer to the SparkBuilder data types section.

Using partial tables

All functions used here must be written for the same datatypes, i.e. the same table structure. In some cases, though, there are data sources that leave out specific columns, and leave the user with a table with fewer columns than required. A reason for this could be a faulty sensor, that doesn't provide a certain column of values.

The function analyzing the data could be written in a way that handles (certain) missing columns, and adapts itself accordingly. For this to work it's necessary that the code produced by the builder doesn't try to convert non-existing columns, and that it creates a corresponding table to be consumed by MATLAB® too. By default, the conversion algorithms will convert all columns part of the original data type specification. If columns are missing, the conversion will fail.

To resolve this situation, the feature PartialTables was implemented. This feature will change the conversion code to only convert columns that are present. This option must be explicitly chosen, and its default is to be turned off. If it's turned on, code will be generated that does this selective conversion, as described above.

It might be argued that always turning on this option would be preferable. Choosing either off or on as default has advantages and disadvantages. The reason for having the option 'off' the default here is that few columns, in general, are optional in a table If the user needs this feature, it should be turned on explicitly, and the code must be written in a way that handles the columns that may or may not be present.

To use this option, turn this typical workflow:

opts = compiler.build.PythonPackageOptions(...
    "algoAC.m", ...
    "OutputDir", "_build", ...
    "PackageName", "exo.ac");

PSB = compiler.build.spark.pythonPackage(opts);

to:

opts = compiler.build.PythonPackageOptions(...
    "algoAC.m", ...
    "OutputDir", "_build", ...
    "PackageName", "exo.ac");

PSB = compiler.build.spark.pythonPackage(opts, partialTables=true);

Using Parallel Computing Toolbox in Spark jobs

Will compiled MATLAB® code in a Spark job run in parallel? The answer is yes, this is exactly what Spark does. When an operation is applied on a Dataframe, Spark will give chunks of data to the algorithm, according to some heuristic that Spark considers the most performant. This can be influenced, if needed, by tweaking certain aspects like the number of partitions in a Dataset, or by doing grouping operations.

As for distributed computing by using MATLAB® Parallel Computing Toolbox™. It can theoretically be used together with Spark, but it's in general not advisable.

Spark is already doing the parallelization, and if there is another tool trying to do the same, they must have intricate knowledge of each other’s schemes in order to do it effectively. As an example, imagine 1 node with 4 cores. Spark runs a MATLAB® algorithm on each core (4x parallelization). In MATLAB®, each core realizes it’s on a 4-core machine, and tries to do a 4-x parallelization, thereby trying to use 16 processes in parallel on a 4-core machine. It should be clear that this will not be an optimal parallelization.

If a compiled MATLAB® function is run on a Spark node without using Spark, parallelization of MATLAB® through Parallel Computing Toolbox™ can be used to improve the performance.

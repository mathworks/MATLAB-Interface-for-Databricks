# Building Wheel libraries with MATLAB

A Wheel library is a Python&reg; package form for a library, and is a file with a
`.whl` extension.

## Introduction

This utility, the `PythonSparkBuilder`, uses MATLAB&reg; Compiler SDK&trade; to create a
Python library, and then generates wrapper code that will enable the use of the
underlying compiled MATLAB&reg; functions in a Spark context.

The methods applied to a Spark DataFrame (`mapInPandas`) or an
RDD (`map`, `mapPartitions`), act on a chunk of a DataFrame. This could
be seen as a table in MATLAB&reg;. Other methods, _User Defined Functions_ (UDFs),
can be applied to one or more columns of a DataFrame.

> Using this functionality has as prerequisites MATLAB&reg; Compiler SDK&trade; (and dependent toolboxes),
> as well as a Python installation and any needed libraries.
> Please see [MATLAB&reg;/Python version compatibility](https://mathworks.com/support/requirements/python-compatibility.html)
> It's important that the Python version and its libraries correspond to the libraries used
> in the Spark installation where it will be used.

## Basic usage

The basic workflow will be described by some simple examples.

### Setup

These examples, located in a directory, something like this:
`/<somewhere>/[Databricks|Spark]/Modules/matlab-spark-api/Software/MATLAB/examples/compiler`

The exact location can be found by executing this in MATLAB&reg;:

```matlab
getSparkApiRoot('examples', 'compiler')
```

This directory contains several MATLAB&reg; functions, that show different examples of
how to write a function, that can be used in a Spark context.

> **Note:** If using the Databricks&reg; package, please also see examples in the directory
> `databricksRoot('examples', 'DatabricksConnect')`

### Building the wheel

All functions are compiled into the same Wheel file, but this is completely arbitrary.
The user decides what files to compile into which library, and separate libraries
could be built for all functions in this example.

Before the functions can be compiled, _schema_ files must be generated.

#### Generating the schemas

The schemas are generated by calling the function
`generateFunctionSchema`
with the name of the function, as well as any arguments for it.

In the first case, `plusPi` just takes a double argument:

```matlab
function pp = plusPi(x)
    pp = x + pi;
end
```

> **Note:** The way schemas are now generated, i.e. generating a `myfun.schema`
> from `myfun.m`, used to be generating a signature `myfun_signature.json`
> from `myfun.m`.
> This is still supported, but discouraged. The new
> _schema_ relies on the schemas used by Apache&reg; Spark&trade;, and so is a better fit.
> It furthermore supports more Datatypes, notably `StructType` and `MapType`.
> The previous method is deprecated and will be removed in a future release.

Generate the schema like this:

```matlab
generateFunctionSchema("plusPi", {33})
```

This will generate a Schema file like this:

```json
{
  "type": "compiler",
  "funcname": "plusPi",
  "fullFilename": "/Somewhere/plusPi.m",
  "inputs": [
    {
      "type": "io",
      "Name": "x",
      "Direction": "in",
      "Table": false,
      "SparkType": "double"
    }
  ],
  "outputs": [
    {
      "type": "io",
      "Name": "pp",
      "Direction": "out",
      "Table": false,
      "SparkType": "double"
    }
  ]
}
```

It's not important that the number 33 was used, just a double value in this case.
Note that the output types weren't specified in the call. They are determined
by MATLAB&reg; calling the function with the argument(s) specified.

This is done to provide the MATLAB&reg; build with more information about the data it
will act on. This takes away some of MATLAB&reg;'s versatility with respect to data types,
but for a good reason. When running on Spark, there is marshalling going on between
Spark, Python and MATLAB&reg;. The marshalling code can be more efficient if it's determined
at compile time what the types are. Furthermore, the Spark Dataframes have specific
types, so it's good to adhere to these types.

> **Note:** More information on this is covered in
> [Function Signatures](FunctionSchemas.md).

The second function, `doMath`, takes 2 double arguments:

```matlab
function [x,y] = doMath(a, b)
    x = -(a + b);
    y = int64(a*b);
end
```

The last function, `addStringCol`, takes a Dataframe as an argument (in Spark).

All the previous code can be found in the function `generateSchemas.m` in
the same directory.

> **Note:** It should be noted that Spark doesn't guarantee that the chunks
> of a sorted table remains sorted. When a table is used in a context where
> ordering is of essence, this should be taken into account.
> As an example, if the table is providing input to a Simulink&reg; model with a
> time vector and a corresponding value, these must be sorted. Simulink&reg; will
> only accept a monotonically increasing time vector, and will fail otherwise.
> Depending on the model, it may also be necessary to shift the first time value
> to be zero.
>
> Furthermore, the resulting Dataframe doesn't have a guarantee on sorting
> either, so if sorting is of essence, the user of that Dataframe must ensure
> this manually, for example using `orderBy` or `sort`.

A typical example for ordering the data used in the MATLAB&reg; function
may look like this:

```matlab
    % Sort the time
    data = sortrows(data, 't');

    % Reset to zero starting time
    data.t = data.t - data.t(1);
```

#### Compiling the code

To compile the code, an option object is first created, and the code is then built
with this:

```matlab
% First create the opts object
opts = compiler.build.PythonPackageOptions(...
    ["plusPi.m", "doMath.m", "addStringCol.m"], ... % the files to compile
    "OutputDir", "_build", ...                 % the output directory
    "PackageName", "mypackagename");                     % the package name

% Then compile the code (note the `spark` in the function name)
PSB = compiler.build.spark.pythonPackage(opts);
```

At this point, there should be a _wheel_ present in the corresponding dist folder:

```bash
$ dir _build/dist/
mypackagename-24.2.0-py3-none-any.whl
```

The code above is also present in `buildLibrary.m` in the same directory.

### Providing the Wheel file to the cluster

If this wheel file is used in a Spark/Databricks environment, the following
steps are required:

To run the file, it must be available on the cluster, and different clusters
may have different options for this.

In the case of Databricks, several methods and options exist to handle the wheel
files more easily.

The `PythonSparkBuilder` class has a method `uploadWheelFile` which will
upload the wheel file to databricks. This method can be called on the result
object of the build. The method takes the path to the wheel file as an optional
named argument `destination` like this:

```matlab
PSB.uploadWheelFile(destination="/Volumes/main/default/myvolume/mywheelfiles");
```

Alternatively, the `compiler.build.spark.pythonPackage' function takes the
optional named argument `wheelDestination`, which allows the user to specify the
future destination of the wheel file. If this was used, the `uploadWheelFile`
can be called as follows:

```matlab
PSB.uploadWheelFile();
```

It's also possible to directly install the wheel file on the cluster using the `installWheelOnDatabricksCluster` method. This used to be the only way to install
a wheel file for use with Databricks, but is now used less, as it is less flexible
compared to methods which _install a wheel file in a Spark Session_. Please refer
to the notes on `%pip install` below.

The method still exists, though, and can be used as follows:

```matlab
PSB.installWheelOnDatabricksCluster("/Volumes/mycatalog/myschema/myvolume/some/directory", clusterId=cluster_id);
```

> **Note:** `addArtifact` is an alternative method of provisioning a library to a Databricks cluster, it is used with Databricks/Spark Connect.
> **Note:** If the cluster defines a library using a policy, thus further libraries cannot
> be installed using the Libraries API. To install the library use the %pip command in a notebook:
> `%pip install /Volumes/mycatalog/myschema/myvolume/some/directory/my.example-24.2.0-py3-none-any.whl`
> If a new version of a library is installed, it may need the additional option `--force-reinstall`
> See Notebook scoped libraries in the [LibraryAPI](../LibraryAPI.md) in the Databricks documentation.

### Importing to the environment

The functions to use with Spark will be created in a module called `wrapper`. In order to
call a specific function, import it from the package.

This code is assumed to be running in a Notebook.

```python
# First, import the Wrapper class of this package
from mypackagename.wrapper import *
```

To simply call a function (will activate the MATLAB&reg; runtime):

```python
# Test the function detectAnomaly
T = plusPi(10.0)
# T == 13.14...
```

`doMath` takes 2 arguments:

```python
M = doMath(5.0, 7.0)
# M == (12,35), a tuple, as two return values
```

`addStringCol` expects a Dataframe with two columns, an `int` and a `double`:

```python
# DF  is a Dataframe as described
OUT = DF.mapInPandas(addStringCol_applyInPandas, addStringCol_output_schema)
OUT.show(3)
```

For the previous function, it needs a pointer to the function
(`addStringCol_applyInPandas`),
as well as the schema of the output
(`addStringCol_output_schema`).
Both are generated, and part of the `wrapper` import.

### Using UDFs

There are different flavours of UDFs that can be used. Not all function signatures can be used as UDFs however.

This will generate the following helper functions that registers the corresponding function as a UDF.
The helper functions for registration (`<fcn_name>_reg_udf*`) are generated with the package.
The shown usage can be done in a notebook.
> **Note:** The usage examples shown here are taken straight from the generated example files,
> and can be used as a starting point.

#### Basic UDF, for use with SQL

```python
def plusPi_reg_udf(spark, name='plusPi_udf'):
    """ Register the function plusPi as a UDF
    A second argument can be used to specify the name to be used."""
    spark.udf.register(name, plusPi, DoubleType())

def doMath_reg_udf(spark, name='doMath_udf'):
    """ Register the function doMath as a UDF
    A second argument can be used to specify the name to be used."""
    spark.udf.register(name, doMath, doMath_output_schema)
```

As can be seen in these definitions, the registered UDFs are given a default name
(`<fcn_name>_udf`), but a different name can be chosen using a second argument.

These can then be used as follows for `plusPi`:

```python
# Register as UDF
plusPi_reg_udf(spark)

# Use the UDF on the temporary table
UDF1 = spark.sql('SELECT X, plusPi_udf(X) FROM temptest_plusPi')
UDF1.show(5, False)
```

And as follows for `doMath`:

```python
# Register as UDF
doMath_reg_udf(spark)

# Use the UDF on the temporary table
UDF1 = spark.sql('SELECT X, Y, doMath_udf(X, Y) FROM temptest_doMath')
UDF1.show(5, False)
```

Evidently, after registering one of the previous UDFs, they can be used in _SQL cells_ too.

```sql
%sql
SELECT X, Y, doMath_udf(X, Y) FROM temptest_doMath
```

#### Basic UDF, for use with Dataframes

```python
def plusPi_reg_udf_dataframe():
```

Use this for `plusPi`:

```python
# Register as UDF for Dataframes
```

And use this for `doMath`:

#### Use a Panda Iterator-Series UDF

These functions are similar to the previous ones, but with the difference
that the input data will be an iterator of Pandas Series objects.
This might be useful when needing to use different batch sizes for memory
reasons, cf. [Setting Arrow&reg; batch size](https://learn.microsoft.com/en-us/azure/databricks/udf/pandas#setting-arrow-batch-size).

```python
def plusPi_reg_udf_series_iter():
    """ Register the function plusPi_series_iter as a pandas_udf function.
    It may be used as follows:
      plusPi_pandas_udf_iter = plusPi_reg_udf_series_iter()
      DF.select(plusPi_pandas_udf_iter(col('arg_x')))
    """
    return pandas_udf(plusPi_series_iter, DoubleType())

def doMath_reg_udf_series_iter():
    """ Register the function doMath_series_iter as a pandas_udf function.
    It may be used as follows:
      doMath_pandas_udf_iter = doMath_reg_udf_series_iter()
      DF.select(doMath_pandas_udf_iter(col('arg_a'), col('arg_b')))
    """
    return pandas_udf(doMath_series_iter, doMath_output_schema)
```

Use it for `plusPi`:

```python
# Register as UDF for Pandas iterator-series
plusPi_udf_series_iter = plusPi_reg_udf_series_iter()

# Use in a Dataframe select statement
UDF4 = DF.select('x', plusPi_udf_series_iter(col('x')))
UDF4.show(5, False)
```

And for `doMath`:

```python
# Register as UDF for Pandas iterator-series
doMath_udf_series_iter = doMath_reg_udf_series_iter()

# Use in a Dataframe select statement
UDF4 = DF.select('a', 'b', doMath_udf_series_iter(col('a'), col('b')))

```

> **Note**: Each environment (Apache Spark, Python and MATLAB&reg;) have a certain
> set of supported data types. Often, there's a direct mapping between some types,
> and for others there's no exact mapping.
> For example, Spark supports (amongst others) `int16`, `int32` and `int64`,
> and so does MATLAB&reg;. Python however, supports one integer type, of potentially
> unlimited bits. This can lead to cases where the implementation difference
> cause numeric differences in output.
> To see a complete list of data types supported with this workflow, please refer
> to the [SparkBuilder data types](SparkBuilderDataTypes.md) section.

## Using partial tables

All functions used here must be written for the same datatypes, i.e. the same
table structure. In some cases, though, there are data sources that leave out
specific columns, and leave the user with a table with fewer columns than required.
A reason for this could be a faulty sensor, that doesn't provide a certain column
of values.

The function analyzing the data could be written in a way that handles (certain)
missing columns, and adapts itself accordingly. For this to work it's necessary
that the code produced by the builder doesn't try to convert non-existing columns,
and that it creates a corresponding table to be consumed by MATLAB&reg; too. By default,
the conversion algorithms will convert all columns part of the original data type
specification. If columns are missing, the conversion will fail.

To resolve this situation, the feature _PartialTables_ was implemented.
This feature will change the conversion code to only convert columns
that are present. This option must be explicitly chosen, and its default is to
be turned off. If it's turned on, code will be generated that does this selective
conversion, as described above.

> It might be argued that always turning on this option would be preferable.
> Choosing either off or on as default has advantages and disadvantages. The
> reason for having the option 'off' the default here is that
> few columns, in general, are optional in a table If the user needs this
> feature, it should be turned on explicitly, and the code must be written in
> a way that handles the columns that may or may not be present.

To use this option, turn this typical workflow:

```matlab
opts = compiler.build.PythonPackageOptions(...
    "algoAC.m", ...
    "OutputDir", "_build", ...
    "PackageName", "exo.ac");

PSB = compiler.build.spark.pythonPackage(opts);
```

to:

```matlab
opts = compiler.build.PythonPackageOptions(...
    "algoAC.m", ...
    "OutputDir", "_build", ...
    "PackageName", "exo.ac");

PSB = compiler.build.spark.pythonPackage(opts, partialTables=true);
```

## Using Parallel Computing Toolbox in Spark jobs

Will compiled MATLAB&reg; code in a Spark job run in parallel?
The answer is yes, this is exactly what Spark does.
When an operation is applied  on a Dataframe,
Spark will give chunks of data to the algorithm, according to some heuristic
that Spark considers the most performant. This can be influenced, if needed, by
tweaking certain aspects like the number of partitions in a Dataset, or by doing
grouping operations.

As for distributed computing by using MATLAB&reg; Parallel Computing Toolbox&trade;.
It can theoretically be used together with Spark, but it's in general not advisable.

Spark is already doing the parallelization, and if there is another tool trying
to do the same, they must have intricate knowledge of each other’s schemes in
order to do it effectively.
As an example, imagine 1 node with 4 cores. Spark runs a MATLAB&reg; algorithm on
each core (4x parallelization). In MATLAB&reg;, each core realizes it’s on a
4-core machine, and tries to do a 4-x parallelization, thereby trying to use
16 processes in parallel on a 4-core machine.
It should be clear that this will not be an optimal parallelization.

If a compiled MATLAB&reg; function is run on a Spark node without using Spark,
parallelization of MATLAB&reg; through Parallel Computing Toolbox&trade; can be used to
improve the performance.
